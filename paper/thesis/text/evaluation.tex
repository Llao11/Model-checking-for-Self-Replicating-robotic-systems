The simulation also revealed the following challenges in the current implementation 
of counterexample-based control:

\begin{enumerate}
    \item non-orthogonality of the end effector to the sides of the part during mechanical attachment.
    \item potential self-intersection of the robot during movement along the path
    of the robot in NSMV for orthogonal connection to parts.
    \item position error due to angle discretization.
    \item error due to simplified representation of the robot structure in NYSMV.
\end{enumerate}

These issues can be resolved in the following system improvements by:

\begin{enumerate}
\item introducing additional constraints on the blocks close to the end 
    of the robot in NYSMV for orthogonal connection to the parts.
\item introducing constraints on self-intersections of robot blocks during movement.
\item iterative reduction of the discretization angle with the introduction of 
    restrictions as the trace is refined.
\item refinement of the robot's geometry in the model.
\end{enumerate}

\subsection{Conclusion}
We validated that checked configurations corresponds to a simulation environment
and that two proposed approaches equivalent to each other.

Sequential checking of the configuration has the following features:
\begin{enumerate}
    \item It gives a full list of all reachable configurations
    \item It allows to further analyze the generated configuration
    \item It is slower in general than aggregated approach
 \end{enumerate}

Aggregated configurations checking from the other hand:
\begin{enumerate}
    \item Is faster than sequential checking for common case
    \item Gives only the first encountered reachable configuration, 
        can find others only after negating the found one.
    \item Allows constraint specific blocks by number in sequence 
        with type defining variable in NuSMV
 \end{enumerate}

\section{Evaluation of 2D reachability checking}

We performed a number of verification experiments using the workflow described in 
Chapter \ref{ch:global} to validate the model and to analyze 
the robot's behavior in various conditions.

% The experiments served two primary purposes: (1) Validation of the 
% model's correctness against expected outcomes in known scenarios, 
% and (2) Performance assessment to understand how the complexity scales 
% with field size and robot length.
%
% Model Validation in Various Scenarios: We tested the model on grid sizes 
% ranging from very small (3x3, 4x4) up to moderate sizes like 7x7. 
% The robot’s assembly sequence length was also varied (we tried sequences of 
% length 2 up to 6 or more parts). We placed parts and obstacles in different 
% configurations, including edge cases:
%
% Scenarios where the robot can immediately find all parts (straightforward success).
%
% Scenarios where one of the required parts is present but located behind 
% obstacles, forcing the robot to take a longer path.
%
% Scenarios where a required part is completely absent from the field (
% which should inevitably lead to failure).
%
% Cases where the robot is boxed in or starts in a tight area, to see 
% if the model correctly identifies the failure (no path) early.

comparing an automatically generated model (for a simple scenario) 
to the hand-written initial model. They matched in structure, and running

Using our Python tool, we measured the 
time required for model generation, model checking, and counterexample processing 
under different scenario sizes. 
We were particularly interested in how the computation grows with:

\subsubsection{ Field Size }
We kept the robot’s sequence length fixed 
and increased the grid size (4x4, 5x5, 6x6, and 7x7)
to see how the state space explosion affects runtime. 
The results, shown in Figure \ref{}, indicated that the verification time grows quickly with 
the area of the grid. 
Intuitively, a larger field means more possible positions 
and more possible paths for the robot, which dramatically increases the 
state space that the model checker must explore. We found that going beyond 
a 7x7 grid with a 4-part robot made nuXmv’s execution considerably slower 
(in our unoptimized model). The relationship was not strictly exponential in 
field size for our tested range, but it was steep—significantly higher 
runtime for each increment in field dimension.

\subsubsection{Robot Length }
We then fixed a field size to 6 and varied the number of parts 
in the robot's sequence (e.g., robot 
of length 3 vs length 4 vs length 5, etc.). The computation times for 
model generation, verification, and trace processing as a function of 
robot size are plotted in Fig. 4. As expected, longer sequences also 
increase the state space (because the assembly\_index has a larger range 
and more parts need to be found in order). This tends to increase the 
length of counterexample traces (successful assembly will have more steps
, since each additional part requires a search sub-loop) and can also 
increase branching (more opportunities to pick up wrong parts, etc.). 
Our measurements showed a noticeable increase in runtime as the robot 
length grew. For instance, with a 6x6 field, going from a robot requiring 
3 parts to one requiring 5 parts made the verification slower, but the 
impact was somewhat less dramatic than increasing the field size. 
This suggests that spatial complexity (field area) was the more limiting 
factor in our model than the temporal length of the task, at least in 
the ranges we tried.

The performance data was collected on a standard laptop (Intel Core i7 
2.4 GHz, running Ubuntu 24.04). We recorded the times for model generation 
(which were negligible for these sizes, on the order of fractions of 
a second up to a couple of seconds for the largest cases), model checking 
(which dominated the time, ranging from under a second for very small 
cases to many seconds or minutes for the larger ones), and counterexample processing 
(also very fast, since parsing a text trace is trivial compared to 
the model checking). Figures 3 and 4 illustrate these trends. In Fig
. 3, for a fixed robot length of 4, the verification time sharply increases 
as the field grows (with, say, 7x7 being substantially slower than 4x4
). In Fig. 4, with field size fixed at 6x6, the curve shows increasing time 
for increasing robot sequence lengths.

One qualitative observation from all our experiments is that the counterexample 
produced by nuSmv was often the shortest possible path to reach the 
goal or failure. That is, the model checker tends to find an optimal or 
near-optimal solution in terms of number of steps, likely because any 
unnecessary wandering would constitute a longer counterexample and model 
checking algorithms often find counterexamples by BFS or iterative deepening 
(thus finding shorter traces first). For example, if there was a more 
direct route for the robot to gather parts, the first counterexample usually 
reflected that direct route rather than a circuitous one. In our tests
, for all evaluated configurations up to length-4 robots in 5x5 grids 
(and many in 6x6), the first counterexample found corresponded to a 
strategy where the robot made efficient moves, not visiting irrelevant areas
. This suggests that, at least for these sizes, our approach could be 
leveraging the model checker as not just a verifier but also a planner that 
yields shortest paths. However, we did not formally guarantee optimality, 
and it is possible for a model checker to output a non-shortest counterexample 
in some cases (especially if heuristics or BDD search orders favor a 
particular exploration). We simply noted this behavior; a more rigorous analysis 
could be done to confirm path optimality or lack thereof. Regardless, 
having a concrete execution trace (shortest or not) is extremely valuable 
for interpreting the system’s behavior.

In summary, the verification experiments confirmed that the NuSMV model 
correctly captures the reachability of both success and failure conditions 
in a self-replicating robot scenario. The automated workflow significantly reduced 
the effort to test different scenarios, and the results provided both 
confidence in the model (through validation tests) and insight into performance 
bottlenecks (through timing measurements). Figures 3 and 4 provide a 
high-level view of how scaling the problem size impacts the computational cost
, which is important when considering more complex or larger-scale applications 
of this verification approach.
