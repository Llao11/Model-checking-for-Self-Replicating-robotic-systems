In this chapter, we describe  a simulation-based platform 
designed and implemented for self-replicating robotic systems, 
combining the ROS 2  middleware, Gazebo physics simulation, 
and a modular set of Python controllers and sensor nodes. 
The principal goal of this platform was not only to design a single robot simulation, 
but also to create an experimental platform that allows us to test, 
compare and validate different control approaches, including  based  on NuSMV, 
for  self-replicating robotic systems.
We structured this simulation system as a collection of ROS 2 nodes and launch 
files that collectively define the robotic environment, the robot itself, 
the material in form of parts, and the control interface. 


\section{System Architecture}

For the simulation we used ROS 2 Jazzy middleware \cite{ROS2Jazzy},  
Gazebo Harmonic simulator \cite{GazeboHarmonic}, 
a set of ROS2 launch files and nodes in Python 3.12. 
The full code base and list of used libraries shown in \cite{GitHub}

The simulated environment consists of three categories of entities:
\begin{itemize}
    \item The main robot, defined in robot.xacro, which acts as an assembler of the new robot.
    \item Material parts, defined in part.xacro, which represent the components that 
    the robot manipulates to assemble a new robot.
    \item The environment represented by base model, described in base.sdf, which provides a 
        fixed reference plane, define optional obstacles and a physical structure for attachment 
        operations of robots.
\end{itemize}

All these elements are spawned into the Gazebo Harmonic simulation using the 
ROS2 launch mechanism.
3D models for these entities were created in SolidWorks 2023 CAD software
based on the design proposed by \cite{Jenett2019MaterialRobot}, 
and converted to STL mesh file.


In order to control this simulation was developed following architecture, 
shown in Figure {fig:SimulationClassDiagram}.

\begin{figure}[h!]
    \centering
    \includegraphics[width=15cm]{SimulationClassDiagram.png} 
    \caption{Class diagram of the simulation system}
    \label{fig:SimulationClassDiagram}
\end{figure}

The system is designed with a layered approach, enabling interaction between 
the user interface, high-level control modules, and ROS 2 nodes communicating 
with Gazebo via the ros\_gz\_bridge. The architecture allows for coordinated manipulation,
sensing, and part assembly in a simulated self-replicating robotic scenario.

We organized the software in several layers, from low-level motion control 
to high-level behavior orchestration:
\begin{itemize}
    \item Initial launch file: robot.launch
    \item Low-level control node: RobotController class, shown in robotController.py.
    \item Material and part interface node: MaterialController and PartController classes,
        shown in partController.py.
    \item Supervisory control node: SRRScontrollerNode, shown in SRRScontrollerNode.py.
    \item Sensor acquisition node: SRRSsensorsNode  class. 
    \item Graphical user interface: GUI class in robot\_controller\_gui.py.
\end{itemize}

We start the simulation by running robot.launch file, it initiates Gazebo world
and starts the graphical user interface. 

GUI class provides the main entry point for user 
interaction. It designed to enable manual and semi-automated control 
of the robotic movement and assembly process. The main functions included in GUI class are: 
\texttt{UI\_setup()}, which initializes the user interface layout, \texttt{move\_part()}
to command manipulations of individual elements, and \texttt{start\_assemble()} 
to trigger the assembly sequence. 
Internally, the GUI maintains a reference to the SRRSController, representing 
the supervisory control logic of the entire system. Through this connection,
user commands are propagated down to robot controller, material 
manager, and sensor interfaces.

The SRRSController class acts as the coordination layer that integrates the 
functional subsystems. It maintains three key associations: the RobotController
, MaterialController, and SensorNode. These relationships form the backbone 
of the system’s modularity, where each controller is responsible for 
a well-defined subset of functionalities. The SRRSController provides functions like 
\texttt{goto\_XYZ()} - to move the free end-effector to given coordinates or 
\texttt{fix\_end()} to fix on the base or on the part for transportation,
that abstract the complexity of low-level motion and interaction control. 
When the user initiates an action through the GUI, the SRRSController 
orchestrates the appropriate response by invoking methods from subordinate controllers.

An object of RobotController class handles direct motion control of the robot 
within Gazebo. It designed  to generate and publish control commands to 
the simulation environment through ROS2 topics. 
This class represents the bridge between high-level assembly planning and low-level joint-
space control, encapsulating motion primitives into callable functions accessible 
by the SRRSController.

The SensorNode component provides perception capabilities. It functions as 
a ROS2 node with several subscribers to Gazebo topics relayed through the 
ros\_gz\_bridge. These topics provide information about joint angles, 
contact states, and detected objects in the simulation. We implemented methods 
such as get\_joint\_angle(), get\_contact1\_state(), get\_contact2\_state(), 
and get\_contact\_object() to access structured sensory information. 
By maintaining real-time synchronization between the Gazebo simulation and 
the ROS2 communication layer, the SensorNode allows the control system 
to react dynamically to physical interactions occurring during assembly—
such as contact detection when two parts align.

The MaterialController manages the set of parts available for 
assembly. It gives a possibility to create and manipulate parts in the Gazebo world, 
using functions create\_parts() and get\_parts(). These parts are represented 
as Gazebo models that can be spawned, attached, or detached through dedicated 
ROS2 launch file. The MaterialController establishes a one-to-many association 
with the PartController, reflecting that a single material manager may 
handle multiple part controllers simultaneously. Each PartController instance 
corresponds to a specific simulated component within the environment.

The PartController provides fine-grained control over individual parts 
in the simulation. It includes methods for creating ROS2 publishers and 
service clients, as well as specialized attachment and detachment procedures 
for various connection points, with corresponding detachment methods. 
The create\_bridge() function establishes the communication link with Gazebo 
through ros\_gz\_bridge, ensuring that changes to part states in Gazebo 
(such as attachment or detachment) are mirrored within the ROS 2 ecosystem. 

Collectively, this architecture enables the robot in simulation to 
perform complex movements and assembly tasks manualy or according to predefined program. 
The GUI layer allows human supervision and intervention, while the SRRSController coordinates 
motion and assembly actions. 
Since each class corresponds to a logical unit of functionality, the 
framework can easily integrate additional controllers, such as vision modules 
or planning algorithms, by extending the existing class hierarchy.

\subsection{Low level robot controller}


The as described in previous section Gazebo model of a robot provides an ability 
to connect to parts and base and to rotate around multiple revolute joints by name
(rev0\_1, rev2\_3, rev5\_6, rev8\_9, rev9\_10 in Listing \ref{lst:JointsControlXacro}) 
allowing high-degree-of-freedom manipulation. 

We developed a separate class RobotController that extends a ROS2 Node 
in order to control this functions on a low level by generating and 
publishing control commands through ROS2 topics. 
Methods of a class include:
\begin{itemize}
    \item  create\_publishers() for initializing communication channels
    \item  goto\_XYZ(x, y, z) for commanding Cartesian movements
    \item  rotate\_joints(ctrl\_sequence) for performing articulated joint rotations. 
    \item  fix\_end() and free\_end() methods are used  to attach or detach end-effectors, 
     mimicking real-world manipulative behaviors. 
\end{itemize}

We modeled the motion of the robot's free end in Cartesian coordinates 
(x, y, z) relative to the fixed base. 
The function goto\_XYZ(x, y, z)  defines the high-level command for moving the 
robot's end-effector to a desired position. 
The function recursively decomposes the trajectory into steps 
on each step if the point is not reachable (length is more than a step length)
robot perform a step movement in target direction, lines 6-28 in Listing \ref{lst:RobotControllerGoto}. 
And when it came closer the function invokes the lower-level function calculate\_joint\_angles() 
to calculate joint angles for necessary target point, line 30 in Listing \ref{lst:RobotControllerGoto}.

\begin{lstlisting}[language=Python, caption={Function goto\_XYZ() of RobotController class}, 
    label={lst:RobotControllerGoto}]
    def goto_XYZ(self, x, y, z, step_size=3):
        x = float(x)
        y = float(y)
        z = float(z)
        # Choose if target point in near or far form (0,0)
        if abs(x) > step_size or abs(y) > step_size:
            # going to a far located point
            if x > step_size:
                stepX = step_size
                x = x - step_size
            elif x < -step_size:
                stepX = -step_size
                x = x + step_size
            else:
                stepX = 0
            if y > step_size:
                stepY = step_size
                y = y - step_size
            elif y < -step_size:
                stepY = -step_size
                y = y + step_size
            else:
                stepY = 0
            # Step algorithm:
            self.goto_XYZ(stepX, stepY, 1)
            self.goto_XYZ(stepX, stepY, 0)
            self.swap_fix_block()  # swap "legs" 
            self.goto_XYZ(x, y, z, step_size)
        else:  # near pose calculation
            command_sequences = self.calculate_joint_angles(x, y, z)
            self.rotate_joints(command_sequences)
\end{lstlisting}

Joint angle calculation function, shown in Listing \ref{lst:RobotController},
serves to calculate joint angles based on chosen combination of blocks and
works only for our blocks parameters.

Mathematically, for a given target point (x, y, z), we compute three internal 
angular parameters:

\[ \alpha = \arcsin(\frac{\sqrt{r_0^2+z^2}}{4}) \]
\[ \beta = \arctan(\frac{y}{x}) \]
\[ r = \sqrt{y^2+x^2} \]
\[ \gamma = \arctan(\frac{z}{r_0}) \]
,where:

$\alpha$ - is a pitch of middle block without correction 

$\beta$ - yaw of a first block

$\gamma$ - correction of $\alpha$

$ r_0=\sqrt{x^2+y^2-1} $ is a correction term depending on the robot geometry. 

These angles are used to derive the five joint commands:
\begin{flalign*}
    & q_1 = \beta_0 \\ 
    & q_2 = \alpha - \gamma  \\
    & q_3 = 180^0 - 2\alpha  \\
    & q_4 = \alpha + \gamma - \sigma^z  \\
    & q_5 = \beta_0  \\
\end{flalign*}

with $\sigma^z$ being a vertical correction term ($0^o$ or $90^o$ depending on z).
The controller converts these degrees to radians and publishes them as 
Float64MultiArray messages to each joint topic "position\_controllerN"
commands. 
The motion is considered complete when the difference between the 
target and current joint angles is below a threshold, in our example it is $\epsilon = 2^o $.

The described approach constitutes an open-loop control with feedback verification: we 
do not continuously adjust the trajectory, but we ensure that each commanded 
position is reached before the next step. The convergence condition is 
implemented through the function \texttt{ wait\_movement\_finish() } using ROS 2 timers and events.

\section{ Base and Part Interaction}

To emulate self-assembly and replication, we introduced attach/detach mechanisms 
between the robot’s end effectors, parts, and base. In the Gazebo simulation
, attachment is realized through service calls bridged from ROS to 
Gazebo’s internal link-joining mechanism. The following attachment states 
are defined:

$A_{R1,B}$ : end-effector 1 attached to base

$ A_{R2,B}$ : end-effector 2 attached to base

$ A_{R1,Pi}$ : end-effector 1 attached to part i 

$ A_{R2,Pi} $: end-effector 2 attached to part i 


Each of these is represented by a ROS topic such as /attach\_end1\_part1 or 
/attach\_part1\_base. Detachment events are the complementary /detach\_* 
topics. The PartController node, shown in Listing \ref{lst:PartController},
automatically creates and maintains all 
necessary publishers for these topics. When a new PartController(
number) instance is created, it initializes a corresponding Gazebo bridge 
through the ros\_gz\_bridge parameter bridge:

Each part is modeled as a single block that can 
attach to either of the robot’s two end effectors or to the base via 
virtual "attachment joints." These joints are controlled through ROS 
topics using the std\_msgs/msg/Empty message type to send attach/detach 
commands, bridged to Gazebo via ros\_gz\_bridge.

/attach\_end1\_part{num}@std\_msgs/msg/Empty@gz.msgs.Empty 

/detach\_end1\_part{num}@std\_msgs/msg/Empty@gz.msgs.Empty 

and similarly for other combinations. Each bridge connects a ROS 2 
topic to a Gazebo message interface, ensuring low-latency coupling between 
control and simulation.

The base model (base.sdf) serves as an inert reference body with defined 
attachment points aligned with the robot’s initial configuration. 
It also defines the inertial frame for all coordinate calculations in goto\_XYZ().
Sensor Integration

The SRRSsensorsNode provides the sensory feedback needed for validation of 
contact and joint dynamics. We subscribe to the following topics:

    /joint\_states – to obtain joint positions and velocities,

    /robot/contact1 and /robot/contact2 – to detect physical interactions between the end effectors and other objects,

    /robot/imu1 – for inertial measurements of base acceleration and orientation.

The SRRSsensorsNode interprets messages of type ros\_gz\_interfaces/
msg/Contacts, parses them to extract collision partner names, and publishes 
simplified string notifications on /contact1/change\_state and /contact2
/change\_state. These allow the controller and GUI to display real-
time contact information.

The contact state logic is time-based: if no new contact message is received for more 
than $\Delta t = 0.5 s$, the system resets the contact flag. This ensures robustness 
against transient or spurious collision events. We use ROS 2 timers to 
evaluate these conditions asynchronously.

The joint angle information from this node is also made available to 
the GUI for continuous visual updates. Through this feedback loop, 
we can evaluate not only the logical success of assembly sequences but 
also the physical consistency of movements and the timing behavior of 
the control algorithms.

\section{Supervisory Control and GUI Integration}

The starting point of the simulation is the launch file \texttt{robot.launch}, 
which initiates the Gazebo world, spawns the robot and the base environment,
and launches the graphical interface for control (\texttt{robot\_controller\_gui.py}). 
The design ensures that the entire system can be initialized with a single command and 
that all subsystems--control, sensing, visualization -- operate concurrently under 
ROS2 multithreaded executor.

High-level behavior orchestration is handled by the SRRScontrollerNode class 
(defined in SRRScontrollerNode.py). This node creates instances of 
both RobotController and PartController and coordinates their interactions. 
It exposes simple methods such as fix\_end1\_part(num), free\_end2\_part(
num), fix\_end1\_base(), and others, which are directly callable from the 
GUI.

The graphical user interface (robot\_controller\_gui.py) constitutes a 
crucial part of the system. It serves as both a human control console and 
an experiment orchestration tool. Built in Tkinter, it allows the operator 
to:

Input target coordinates (X, Y, Z) and issue movement commands.

Fix or release robot ends or parts through dedicated buttons.

Observe current joint angles, contact states, and camera feeds.

Execute the automatic assembly process via start\_assemble().
The robot\_controller\_gui.py file launches and connects all these nodes,
forming the interactive entry point to the SRRS simulation. The GUI shown in Figure \ref{fig:simGUI} 
is implemented in Tkinter, providing manual and automated control capabilities,
live feedback of joint states, and camera streams. 

\begin{figure}[h!]
    \centering
    \includegraphics[height=8cm]{simGUI.png} 
    \caption{Graphical user interface for simulation control}
    \label{fig:simGUI}
\end{figure}

When the "Start Assemble"
button is pressed, the GUI calls start\_assemble(), which executes an 
automated sequence of motions to assemble a new robot from scattered parts.


The GUI continuously updates sensor readings using scheduled callbacks (
root.after()), ensuring a refresh rate of approximately 30–100 ms for 
angles and contact information. Camera frames are displayed using Pillow
’s ImageTk interface, showing two synchronized camera streams from Gazebo 
topics /camera1/image and /camera2/image.

When the user initiates start\_assemble(), the GUI executes a predefined sequence:

Fix the first end of the robot to the base.

Release all part connections.

Set assembly coordinates (typically (2, –2, 0)).

Move to each part, pick it up, and place it at the assembly location.

Increment the z-coordinate for each subsequent layer.

This sequence is implemented in the method move\_part(num, x, y), which 
demonstrates a loop of high-level pick-and-place actions using the primitive 
goto\_XYZ() calls and attachment commands. Each movement is performed in 
small steps to avoid collisions, and the GUI waits for the movement threads 
to complete before issuing the next command.

\subsubsection{ Launch and Execution Pipeline }

The entire simulation is initiated through robot.launch, which performs the 
following actions sequentially:

Launches the Gazebo Harmonic world with the base model loaded (base.sdf).

Spawns the robot using robot.xacro through the standard ros2 run ros\_gz\_sim create command.

Spawns several parts defined in part.xacro distributed across the environment.

Starts the GUI and underlying control nodes (SRRScontrollerNode, SRRSsensorsNode
, and camera subscribers).

The environment thus initialized represents a closed-loop experimental setup 
where the robot perceives, acts, and interacts with parts and the base 
under simulated physics. Because ROS 2 Jazzy supports real-time communication 
and multithreading, the GUI and control nodes can run in parallel without 
blocking, enabling responsive interaction.

\subsubsection{ Control Strategy Validation Framework }

The main purpose of this project was to create a validation framework for 
different control strategies rather than to fix a single deterministic behavior.
Within our architecture, alternative controllers can be plugged in 
at several levels:

Kinematic policy: replacing the calculate\_joint\_angles() function with a neural or optimization-based inverse kinematics solver.

Trajectory planning: modifying goto\_XYZ() to use continuous path generation instead of recursive steps.

Assembly sequencing: altering start\_assemble() to implement adaptive planning based on part detection or reinforcement learning.

Sensor fusion: integrating visual feedback from the camera nodes to enable autonomous part localization.

The modular design of ROS 2 nodes facilitates this substitution without 
affecting the overall system. For example, the RobotController class exposes 
clear interfaces (rotate\_joint(), rotate\_joints(), goto\_XYZ()), and 
the communication topics are standardized. Therefore, any new controller can 
publish to the same topics and subscribe to the same sensor messages, ensuring compatibility.

Validation is achieved by comparing the success rate, time to completion, 
and energy metrics (approximated by cumulative joint rotations) of 
different strategies. The GUI’s visual and logged data provide qualitative insights
, while the ROS 2 message traces can be quantitatively analyzed.

St , each describing the configuration of all parts and the robot at 
time t. Each state includes the position vector of the robot end

\subsection{Implementation Challenges and Design Considerations}

Developing this system required addressing several challenges intrinsic to both ROS 2 and Gazebo:

Synchronization of simulated physics and ROS 2 communication. Gazebo Harmonic 
introduces slight delays in joint updates; therefore, we implemented event
-based waiting (threading.Event) rather than time-based sleeps to detect 
motion completion.

Attachment semantics. Because Gazebo joint creation for attachments can introduce instabilities
, we used lightweight Empty message topics rather than service calls, improving responsiveness.

GUI concurrency. To prevent blocking of ROS 2 threads by Tkinter, 
we ran the ROS 2 executor (MultiThreadedExecutor) in a separate daemon 
thread, allowing GUI and simulation updates to coexist without race conditions.

Scalability. The number of parts can be increased dynamically using spawn\_part
(). This function invokes a new ROS 2 process through a Bash command that 
calls ros2 run ros\_gz\_sim create, ensuring that each part receives a 
unique name and topic namespace.

Extensibility. Because each node is encapsulated, new sensors or controllers 
can be added by extending the base class rclpy.node.Node.

Through this architecture, we achieved a balance between scientific flexibility 
and practical usability.

\section{Simulation Workflow}

In a typical experiment, we initialized the simulation with the robot fixed at the base 
and three parts distributed at different coordinates. When we executed the 
automated assembly via start\_assemble(), the robot alternated between fixing 
one end to the base, moving the free end to a part, attaching it, 
and transporting it to the assembly point. This process was visualized in 
Gazebo and confirmed through GUI feedback of contact states.

We observed that the recursive stepping algorithm ensured stable motion 
without overshoot. The joint convergence tolerance of 2 degrees provided 
reliable positioning, and the end-effector’s attach detach operations were 
successfully synchronized with the movement sequence. The assembled structure 
maintained physical integrity under Gazebo’s physics engine, confirming that 
the connection logic and control synchronization were valid.

Extensibility Toward Autonomous Self-Replication

While our current implementation focuses on deterministic sequences, 
the architecture inherently supports higher-level autonomy. By replacing the 
manual coordinate inputs with vision-based part detection, the robot could 
identify parts automatically and plan assembly paths. The SRRScontrollerNode can 
be extended to integrate a planning layer using the MoveIt 2 framework or 
a reinforcement learning policy trained via the ROS 2–Gazebo interface.

Furthermore, because all messages are standard ROS 2 types, the same 
system could be deployed on physical robots with appropriate hardware drivers
. The self-replication process would then move from simulation to reality
, enabling experimental validation of robotic “growth” behaviors.

\subsection{Conclusion}

Through the development of this project, we established a modular and 
extensible simulation environment for studying self-replicating robotic 
systems. Our implementation demonstrates that the integration of ROS 
2 Jazzy and Gazebo Harmonic provides a sufficiently realistic and flexible 
platform to test control strategies involving attachment, detachment, 
and multi-body coordination. The structure of the codebase—especially the 
clear separation between RobotController, PartController, and SRRSsensorsNode
enables straightforward substitution of alternative algorithms, whether 
model-based or data-driven.

In terms of validation, we confirmed that deterministic control sequences 
can reliably assemble multiple parts into a replica structure under physics
-based constraints. The architecture also provides quantitative metrics 
such as joint trajectories, contact durations, and execution times, 
allowing systematic evaluation of alternative strategies.
